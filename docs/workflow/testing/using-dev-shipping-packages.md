# Тестирование с Dev Shipping Packages и .NET SDK

Инструкции ниже демонстрируют использование пакетов Dev Shipping из вашей сборки репозитория runtime для тестирования, запуска приложений и других задач. Это самый длительный, но наиболее приближенный к реальному использованию метод тестирования CoreCLR.

Помимо этого сценария имеются подробные инструкции по другим способам тестирования:

-   [Тестирование с .NET SDK](using-your-build-with-installed-sdk.md)
-   [CoreRun и CoreRoot](using-corerun-and-coreroot.md)

## Требования

В следующих подразделах описаны требования, а также инструкции по подготовке этих требований.

### Сборка пакетов Dev Shipping {#shipping}

Shipping Packages состоят из четырёх подмножеств (subsets) репозитория runtime: Clr, Libraries, Packs и Host. Чтобы собрать их, выполните следующую команду из корня репозитория:

Для Windows:

```cmd
.\build.cmd -s clr+libs+packs+host
```

Для macOS и Linux:

```bash
./build.sh -s clr+libs+packs+host
```

Это создаст несколько установщиков, NuGet-пакетов, архивов и других файлов в папке `artifacts/packages/<configuration>/Shipping`. Можно установить сборку runtime на ваш компьютер с помощью этих установщиков, однако это не рекомендуется.

### Получение последней версии .NET SDK

В [репозитории SDK](https://github.com/dotnet/sdk#installing-the-sdk) есть ссылки на все nightly-сборки для всех поддерживаемых платформ. Найдите ту, которая подходит для вашей системы, и скачайте её.

Чтобы настроить nightly-SDK, вы можете либо установить его на ваш компьютер, либо использовать портативную сборку. Если вы скачали установщик, просто следуйте стандартным инструкциям по установке.

Чтобы использовать портативную сборку (рекомендуется), сначала извлеките скачанный _zip/tar.gz_ в любое место. Затем вы можете либо добавить путь к извлечённой папке в переменную окружения `PATH`, либо всегда указывать полный путь к `dotnet` (например, `/путь/к/ночной/сборке/dotnet`).

После настройки нового dotnet вы можете проверить, что используете новую версию, выполнив команду `dotnet --version`. На момент написания версия должна быть равна `9.0.100-*` и выше.

## Создание и запуск приложения

После выполнения вышеуказанных операций создайте и настройте тестовое приложение как показано ниже.

### Настройка приложения

Сначала создайте простое консольное приложение, например:

```bash
mkdir HelloWorld && cd HelloWorld
dotnet new console
```

**ПРИМЕЧАНИЕ**: Убедитесь, что вы используете ночной SDK, который должен быть установлен как показано на предыдущем шаге.

Затем нам нужно сообщить SDK, что собранные NuGet-пакеты готовы и их нужно использовать. Для этого создайте файл `NuGet.Config` в папке приложения с помощью команды `dotnet new nugetconfig`.

Этот файл конфигурации потребует нескольких изменений, чтобы работать так, как нам нужно. Сначала создайте папку, где NuGet будет кэшировать свои данные локально для этого эксперимента. В этом примере она называется `LocalNugetCache`. Затем отредактируйте ваш конфигурационный файл:

```xml
<configuration>

  <config>
    <!-- Установите "value" здесь на папку, которую вы будете использовать для локального кэша NuGet. -->
    <add key="globalPackagesFolder" value="Path/To/LocalNugetCache" />
  </config>

  <packageSources>
    <!-- Чтобы унаследовать глобальные источники пакетов NuGet, удалите строку <clear/> ниже -->
    <clear />

    <!-- Любые пакеты, которые могут понадобиться, но отсутствуют в вашей сборке, будут взяты из последнего NuGet-фида. -->
    <!-- Подробнее: https://github.com/dotnet/sdk#installing-the-sdk -->
    <add key="dotnet9" value="https://pkgs.dev.azure.com/dnceng/public/_packaging/dotnet9/nuget/v3/index.json" />

    <!-- Установите этот путь на место, где находятся ваши Shipping Artifacts. В этом примере предполагается сборка в конфигурации 'Debug'. -->
    <add key="local runtime" value="Path/To/Runtime/artifacts/packages/Debug/Shipping" />
  </packageSources>

</configuration>
```

После того как файл `NuGet.Config` готов, нам нужно сообщить нашему проекту, что мы будем использовать другой runtime. Добавьте следующее в файл `csproj` вашего приложения:

```xml
<ItemGroup>
  <!-- На момент написания '10.0.0-dev' — это версия Shipping Packages репозитория runtime. -->
  <FrameworkReference Update="Microsoft.NETCore.App" RuntimeFrameworkVersion="10.0.0-dev" />
</ItemGroup>
```

Если вы не уверены какие версии ваши пакеты используют, проверьте версии в именах файлов. Например, выберите файл `nupkg`, который будет использоваться с вашим приложением, из папки Shipping (`artifacts/packages/<конфигурация>/Shipping`). Его имя будет выглядеть как `Microsoft.NETCore.App.Runtime.win-x64.10.0.0-dev.nupkg`, в зависимости от текущей версии и вашей конечной системы.

### Пример теста

Для демонстрации работы тестовое приложение будет выводить версию runtime:

```csharp
using System.Diagnostics;

var coreAssemblyInfo = FileVersionInfo.GetVersionInfo(typeof(object).Assembly.Location);
Console.WriteLine($"Hello World from .NET {coreAssemblyInfo.ProductVersion}.");
Console.WriteLine($"The location of System.Private.CoreLib.dll is '{typeof(object).Assembly.Location}'");
```

### Публикация и запуск приложения

Следующая команда соберёт и опубликует ваше приложение:

```cmd
dotnet publish -r win-x64
```

Измените `win-x64` в соответствии с вашей операционной системой и архитектурой.

Запуск этого приложения должен вывести следующее:

```text
Hello World from .NET 10.0.0-dev
The location of System.Private.CoreLib.dll is '/path/to/your/app/bin/Debug/net10.0/win-x64/publish/System.Private.CoreLib.dll'
```

## Внесение изменений и использование обновлённых пакетов

Теперь вы успешно протестировали вашу сборку runtime. Однако, скорее всего, вы будете вносить дальнейшие изменения, которые захотите протестировать. Проблема здесь в том, что вы не можете просто пересобрать репозиторий и ожидать, что всё заработает. Это связано с вышеупомянутым кэшем NuGet. Поскольку локально номер версии не меняется, NuGet не понимает, что изменения были внесены, поэтому использует кэшированную версию. Для обхода проблемы нужно удалить этот кэш. Именно поэтому мы установили локальный кэш с помощью `globalPackagesFolder` в файле `nuget.config`.

Итак, шаги для применения и тестирования изменений следующие:

1. Пересоберите runtime, как показано в разделе "[Сборка пакетов Dev Shipping](#shipping)". Обратите внимание, что если вы вносите изменения только в CoreCLR (clr) или библиотеках (libs), вы можете собрать только необходимое.
2. Удалите локальный кэш NuGet.
3. Снова опубликуйте и запустите ваше приложение.

Теперь ваше приложение будет использовать обновлённый пакет.
